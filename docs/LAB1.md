# Lab 1：分布式协议可视化

《操作系统与分布式系统》实验一。

---

## 实验目标

课上讲了很多分布式协议，但光看课件很难直觉地理解它们在真实网络下的行为——消息乱序、节点崩溃、网络分区……这些异常究竟会让协议"在哪里"出错，靠文字描述很难感受。

本实验的目标是：**亲手实现课上讲到的分布式协议，并用可视化平台演示它在不同场景下的行为**——包括一切正常时，以及注入故障后发生了什么。

完成后你应该能回答：

- 这个协议在正常网络下消息是怎么流动的？
- 如果某个节点崩溃，或者两段网络被隔断，协议会卡在哪里？
- 课上提到的某个关键设计（比如"投票前先写日志"），如果去掉它会有什么后果？

## 一、平台快速上手

这一节帮你在 10 分钟内跑起第一个协议实验。建议先把流程走通，再开始写代码。

### 1.1 创建协议

点击侧栏「我的协议 → 新建协议」，选择「**从本地协议目录发现代码**」，路径填 `protocols/`（相对于项目根目录）。平台会列出目录下已有的协议供你参考；你也可以选「空白 Go 项目」从头写。

每个协议是一个独立的 Go module，放在 `protocols/你的协议名/` 目录下。平台自动发现 `main.go`、`protocol.go` 等文件，你在浏览器里就能编辑、保存、运行。

### 1.2 实验的三层结构

平台把工作分成三层：**协议 → 实验 → 运行**。

- **协议**：一份 Go 代码，定义了节点做什么。你对协议代码的每次修改，对它下面所有实验的后续运行都生效；已有的运行记录不变。
- **实验**：一组参数（节点数、延迟、故障模式）。同一份代码可以有多个实验，比如"3 节点正常网络"和"5 节点高延迟"可以分别保存为两个实验。
- **运行**：点击「运行实验」产生一次实际运行。运行记录永久保存，可以回放，也可以导出为 JSON。

你做每个观察场景时，通常需要创建一个对应的实验，然后「运行实验 → 按步骤注入故障 → 观察时空图」。

> 平台每次只能运行一个实验。如果试图在已有实验运行时启动另一个，新的运行会报错。结束当前实验后再启动新的，或在同一协议下建多个实验分别管理不同场景。

### 1.3 运行你的第一个实验

1. 在协议下创建一个实验，节点数填 3，延迟填 200ms，运行环境选「**内置仿真**」（不需要 Docker，立刻能用）。
2. 点「运行实验」，进入可视化界面。
3. 点任意节点，弹出面板里有「在 node-x 运行」：在该节点上运行一个业务操作（例如 Put、Acquire）。
4. 在「时空图」视图里，每条箭头是一条消息，每个彩色方块是一次状态上报；点击箭头可以看到完整 payload。
5. 点「暂停」→ 左右拖动底部时间轴，可以逐步回放任意历史状态。

> 💡 内置仿真和真实 Docker Go 节点的区别：仿真执行的是平台内置的 JavaScript 参考实现，**不运行你写的 Go 代码**；Docker 模式才真正编译并运行你的 Go 程序。写代码阶段先用仿真验证场景理解，调试代码时切换到 Docker。

### 1.4 故障注入

点击节点，弹出面板里有三类操作：

- **在 node-x 运行**：在该节点上运行业务操作（Put/Get/Propose/Acquire……）
- **崩溃 / 恢复**：模拟节点进程崩溃（`docker kill`）和重新启动
- **链路**：为「该节点 ↔ 其他节点」设置单向或双向的中断、固定延迟、带宽限制

顶部控制条的「网络」菜单可以一键「恢复全部链路」，不会恢复已崩溃的节点。

### 1.5 时空图与回放

时空图是实验的主要观察工具。横轴是时间，每行是一个节点：

- **实线箭头**：消息已被目标节点收到
- **虚线箭头**：消息发出但尚未到达（在网络里）
- **红色 ×**：消息被丢弃（节点已崩溃、链路中断、随机丢包）
- **彩色方块**：节点通过 `node.Report(...)` 上报的状态变化；点击可以看完整 JSON

时空图按事件的实际时间戳绘制——一条跨两个节点的斜线箭头，斜率就是消息的实际传播延迟。

## 三、L03 时间与时钟

### 3.1 Cristian 时钟同步

**对应课件**：L03

**算法要点**：客户端向时钟服务器发 RPC，记下发送时刻 $T_0$ 和返回时刻 $T_1$，用服务器返回的时间 $T_s$ 加上估算的网络延迟 $(T_1 - T_0) / 2$ 来校正本地时钟。

平台中每个节点有一个模拟的本地时钟（初始偏移和放大的漂移率），而不是直接用系统时钟——这样才能在同一台机器上演示不同节点"时钟不同步"的问题。

> 以下场景中提到的状态字段名（`errorMs`、`lastSync` 等）是**建议**使用的接口名称，方便和本文档对照。你也可以选用自己的命名，但请在协议 README 中说明各字段含义。

**观察场景 A（正常情形）**：对称延迟下的一次同步

1. 查看各节点初始的 `errorMs`——它们都不是零。
2. 从 node-2（客户端）向 node-1（时间服务器）发起 `Sync`。
3. 同步后 node-2 的 `errorMs` 应该接近零。
4. 打开时空图：能看到 RPC 请求和回复的箭头，以及 node-2 在回复里携带的时间戳。

**观察场景 B（非对称链路）**：单向延迟不等时的误差

把 node-1→node-2 的链路延迟设为 200ms，node-2→node-1 设为 2000ms（或反过来）。再做一次同步，观察 `errorMs` 的变化。Cristian 算法假设往返延迟对称；不对称时误差有多大？

### 3.2 NTP（Network Time Protocol）

**对应课件**：L03

**算法要点**：NTP 记录四个时间戳 $t_0$–$t_3$，计算 `offset = ((t1-t0) + (t2-t3)) / 2`，`delay = (t3-t0) - (t2-t1)`。实际部署中每个 NTP 客户端做 8 次测量，取 `delay` 最小的那次的 `offset`——因为 `delay` 最小意味着网络最对称，那次的偏移估算最准。

`stratum` 表示时钟层次：stratum-1 是直连原子钟的节点，stratum-2 从 stratum-1 同步，误差会随层次累积。

**观察场景 A（服务器处理时间被扣除）**：服务器处理请求需要一些时间，这段时间不该被算入网络延迟。打开时空图，看消息的实际收发时间，验证 $t_2 - t_1$ 就是服务器处理时间，它被正确地从 delay 计算中去掉了。

**观察场景 B（最小 delay 过滤）**：发起一次 `Sync`（内部做 8 次测量，把链路抖动设大一些），观察 `lastSync.samples` 里每个样本的 delay 值（格式如 `node-1 d=200 o=+15 ←`，`←` 标记最终选中的那次）。最终选用的是哪次？为什么选 delay 最小而不是选 offset 最小？

**观察场景 C（误差随 stratum 累积）**：设置 node-1 → node-2 → node-3 的同步链（node-1 是 stratum-1），比较三个节点最终的 `errorMs`。

### 3.3 Berkeley 算法

**对应课件**：L03

**算法要点**：master 向所有节点询问各自的本地时钟，排除明显离群的，对剩余的取平均，然后告诉每个节点要调整多少毫秒。关键：不是让每个节点同步到 master 的时钟，而是所有节点收敛到同一个（人工计算的）平均值。时钟只能向前调（平滑增加速率），不能突然跳变——跳变会导致时间倒退，破坏依赖时间单调递增的应用。

**观察场景 A（周期轮次收敛）**：启动后等几个同步周期，观察各节点的 `errorMs` 是否收敛到一个较小的范围内。注意"较小"不等于"接近零"——Berkeley 算法的目标是节点间**相互一致**，不是同步到真实时间。

**观察场景 B（离群时钟不参与平均）**：手动用 `SetClock` 把某个节点的时钟偏移设为很大的值（比如 +10000ms），观察 master 是否排除了它。若不排除，平均结果会被严重拖偏；若排除，其余节点能正常收敛。

**观察场景 C（跳变 vs 平滑调整）**：在节点状态里找 `lastAdjMs`（本次调整量）和 `slewMsLeft`（平滑调整剩余时间）字段，对比 `SetMode(step=true)`（跳变）和 `SetMode(step=false)`（slew 平滑调整）时各节点时钟的轨迹。思考：对于依赖"时间不倒退"假设的应用（如日志、缓存过期），跳变会带来什么问题？

**设计变体**：master 崩溃后选举不在本协议范围内（协议本身没有 master 自动选举），但可以演示：等待时钟收敛后崩溃 node-1（master），等待若干轮次，观察各节点按各自漂移率重新分开——轮次停止，时钟不再收敛；恢复 node-1 后轮次恢复，时钟重新收敛。这和 Bully 选举的场景形成对照——时钟同步需要一个活跃的协调者。

### 3.4 Lamport 时钟与向量时钟

**对应课件**：L03

这个协议没有业务逻辑，它演示的是两种时间戳的**性质**，不是一个"服务"。你的任务是产生一些事件，然后用 `Compare` 验证时钟的数学性质。

**关键性质**（不要死记，要能从时空图上验证）：

- Lamport：`e → e'` ⟹ `L(e) < L(e')`，但反之不成立——`L(e) < L(e')` **不能**推出 `e → e'`。
- 向量：`V(e) < V(e')` **当且仅当** `e → e'`；不满足这个关系的两个事件是并发的。
- 全序时间戳 `L.node` 可以对所有事件定一个全序，但这个顺序对并发事件来说是任意的（打破平局用的节点编号没有物理含义）。

**观察场景 A（课件第 37 页的图）**：按课件图中的事件顺序发送消息，然后用 `Compare` 验证：`b` 和 `e` 的 Lamport 值哪个更大？向量比较的结果是什么？（期望：`L(b) > L(e)` 但 `vector = concurrent`。）

**观察场景 B（Lamport 相等的并发事件）**：让三个节点各自发生一个本地事件，不发任何消息，三个事件的 `L` 都应该是 1。用 `Compare` 验证它们两两并发。全序时间戳会给它们排一个先后（1.1 < 1.2 < 1.3），这个顺序有没有物理意义？

**观察场景 C（自动事件后的不变式）**：开启 `Auto` 模式，让节点随机产生事件，一段时间后停下。手动挑几对事件用 `Compare`，检查：凡是向量判定有因果的（`vector = a→b` 或 `b→a`），Lamport 顺序一定与之一致（`agrees = true`）。反过来，Lamport 顺序一致的事件，向量可能是并发的。

## 四、L04 互斥与选举

这一讲的四个互斥算法（集中式、Lamport、Ricart-Agrawala、多数投票）使用**相同的应用输入接口**（`Acquire(holdMs)`、`Auto(...)`）和**相同的状态字段**（`role`、`entries`、`lastWaitMs`、`messagesSent`）。这是故意设计的——方便你对照课件里的的比较表，在同一个实验框架下比较不同算法的消息开销和容错性。

### 4.1 集中式互斥

**对应课件**：L04

**算法要点**：协调者（`coordinator`，固定为 node-1）维护一个 FIFO 请求队列。想进临界区的节点发 `Request`，收到 `Grant` 才能进入，退出时发 `Release`。每次互斥需要 3 条消息（Request → Grant → Release），代价是协调者是单点。

**观察场景 A（正常情形）**：3 个节点同时发 `Acquire(holdMs=2000)`，在时空图里数消息，验证每次进出临界区确实是 3 条。看 `entries` 计数器确认同一时刻只有一个节点的 `role=critical`。

**观察场景 B（协调者崩溃）**：有节点在等待 `Grant` 时崩溃协调者，观察等待者会一直阻塞——它发出的 `Request` 永远得不到回复。这是集中式互斥的致命弱点：协调者不可用，所有人都卡死。

**设计变体（协调者重启失忆）**：这是核心的变体场景。步骤：
1. 某节点已持有锁（`role=critical`）；
2. 崩溃并恢复协调者——协调者**不持久化**队列状态（关闭持久化模式）；
3. 另一个节点在协调者重启后发 `Request`，协调者没有任何记录，直接发 `Grant`；
4. 此时两个节点同时认为自己持有锁，互斥被破坏。

打开持久化后再复现同样步骤，验证重启后协调者正确恢复队列，不会双重授权。

### 4.2 Bully 选举（必选）

**对应课件**：L04

**算法要点**：目标是选出**存活节点中编号最大**的节点作为协调者。任何节点发现协调者失效时发起选举：向更高编号节点发 `Election`，收到 `OK` 说明有更高节点接管，没收到 `OK` 则自己获胜并广播 `Coordinator`。

**观察场景 A（启动选举）**：5 个节点启动后会自动选举，node-5（最高编号）应该获胜。在时空图里观察 `Election` / `OK` / `Coordinator` 三种消息的流向——和课件插图比较。节点状态 `sent` 记录了各自发出的消息数；全体 $n$ 个节点同时发起时，总消息数是 $O(n^2)$。

**观察场景 B（协调者崩溃）**：崩溃 node-5，等超时触发后观察重新选举的过程。node-4 发起，发 Election 给 node-5 无人回应，最终 node-4 获胜。在时空图里能清楚看到"向上发 Election、没有 OK、广播 Coordinator"的序列。

**观察场景 C（课件 7 节点示例）**：用 7 节点实验，崩溃 node-7，手动让 node-4 `StartElection`，在时空图里逐步复现课件里的插图。

**观察场景 D（最多两个节点同时崩溃）**：...

**设计变体（旧协调者恢复后"夺权"）**：恢复被崩溃的 node-7，观察它启动后会发起选举并重新成为协调者。这个行为是 Bully 算法的特性，也是它的争议所在——如果节点是因为暂时过载（而不是真正崩溃）被误判失效，恢复后立刻夺权可能造成频繁的 leader 切换。思考：什么场景下这是合理行为，什么场景下是问题？

### 4.3 Lamport 互斥

**对应课件**：L04

**算法要点**：完全去中心化，没有协调者。每个节点广播 `Request` 请求，收到别的节点的 `Reply` 后按**时间戳全序**排队；队头是自己、且已经收到了所有节点的 `Reply` 时才能进入临界区，退出时广播 `Release`。

关键约束：`Reply` 必须延迟到对方的时间戳排在自己请求之后才发出，保证优先级高的请求不会被抢占。任何一个节点崩溃都会导致所有人永远等不到它的 `Reply`，陷入阻塞。

**观察场景 A（两节点同时请求）**：node-1 和 node-3 同时发 `Acquire`，在时空图里观察各自的 `Request` 时间戳和 `Reply` 的交叉——时间戳更小（优先级更高）的节点先进临界区。

**观察场景 B（任一节点崩溃阻塞）**：某节点在没有请求临界区时崩溃，观察其他节点在发起请求后会无限等待那个已崩溃节点的 `Reply`。这说明即使和当前互斥完全无关的节点崩溃，也会阻塞所有人，这是 Lamport 互斥的主要缺陷之一。

**设计变体（消息开销对比）**：Lamport 互斥每次进出临界区需要 $3(n-1)$ 条消息（n 节点）；而 Ricart-Agrawala 可以做到 $2(n-1)$。为什么？观察 `messagesSent` 字段，对比两个协议在相同场景下的消息数。

---

### 4.4 Ricart-Agrawala

**对应课件**：L04

**算法要点**：对 Lamport 互斥的优化。不再发独立的 `Release` 消息，而是把"释放"折叠进下一个请求的回复里：持有临界区时收到的请求先缓存，退出时一次性全部回复，减少一轮消息。

**观察场景 A（两节点同时请求）**：复现课件里的例子，node-1 和 node-3 同时 `Acquire`，时间戳更小的先进。在 `lastWaitMs` 字段里可以看到等待时间。

**观察场景 B（无关节点崩溃也阻塞）**：和 Lamport 一样，不在请求队列里的节点崩溃后，有人发起请求就会阻塞——它的 `Reply` 永远不会到。这是两个算法共同的弱点。

**观察场景 C（指数抖动网络下的随机负载）**：实验延迟改为指数分布，让 5 个节点随机频繁 `Acquire`，用 `Auto` 模式。观察：消息乱序（后发的先到）是否会破坏互斥？平台默认每条链路保持 FIFO 顺序（像 TCP），所以不会；但如果换成 `ordering: unordered`（见平台 API 文档），结果会怎样？

---

### 4.5 多数投票互斥

**对应课件**：L04

**算法要点**：节点向所有其他节点请求投票（`Vote`）；收到多数票（超过 $\lfloor n/2 \rfloor$）就进入临界区，退出时广播 `Release` 释放投票。每个节点对同一个时刻只投一票，保证最多一人获得多数。

关键弱点：投票者崩溃并重启后会**忘记**自己投给了谁，重新接受投票，可能导致两人同时获得"多数"。持久化投票记录可以避免这个问题。

**观察场景 A（无竞争一次成功）**：只有一个节点发起，观察投票的收集过程和进入临界区。

**观察场景 B（全体同时申请，分票与退避）**：所有节点同时发起 `Acquire`，每人只拿到部分票，没人够多数，所有人退避并重试。观察 `lastWaitMs` 和重试次数。

**设计变体（投票者重启遗忘选票）**：
1. node-1 已收到多数票正在临界区；
2. 其中一个投票者崩溃并恢复；
3. node-2 在投票者恢复后发起请求，该投票者**没有持久化记录**，认为自己还没投票，于是投给 node-2；
4. node-2 也凑够了多数票，两人同时进入临界区——互斥被破坏。

持久化修复：投票者在回复 `Vote` 之前写盘，重启后知道自己已经投给了谁，不会重复投票。

## 五、L05 复制与共识

### 5.1 主备复制

**对应课件**：L05

**算法要点**：node-1 是主副本，其余是备份。写请求可以发到任何节点，备份会转发给主副本。主副本分配递增的日志序号（`index`，相当于 zxid），再按序向备份发送。

复制模式：
- `async`：主副本应用后立即回复客户端，备份稍后收到。快，但能读到旧数据。
- `sync`：主副本等所有备份确认后才回复。慢，任一备份不可达时写入超时出错。

读取模式：
- `local`：读本地，快，可能过期；
- `primary`：读主副本，线性一致；
- `session`：带上上次写的 `index`，备份等本地追上后才回，保证"读己之写"。

**观察场景 A（异步复制过期读）**：
1. `Mode(async, replicationDelayMs=4000)` 让备份延迟 4 秒收到更新；
2. 在 node-2 上写 `Put(x, 1)`，写立刻成功；
3. 立刻在 node-2 本地读 `Get(x, mode=local)`——读不到，`stale=true`；
4. 改为 `primary` 读——读到 1；
5. 用 `session` 读并带上 `minIndex=1`——等约 4 秒后返回。

观察 `waitedMs` 字段，理解 session 读的等待机制。

**观察场景 B（同步复制与备份崩溃）**：
1. `Mode(sync)`；写 x=1 成功；
2. 崩溃 node-3，再写 x=2——4 秒超时后返回错误，但 x=2 已经在主副本和 node-2 生效了；
3. 客户端看到"失败"，数据却已部分写入——超时不等于没执行。

**设计变体（没有自动故障转移）**：主副本固定为 node-1，它崩溃期间写入和 `primary` 读全部不可用。这说明主备复制需要一个更上层的机制（如 Raft 共识）来决定谁是主副本，否则无法自动恢复。

---

### 5.2 Quorum 复制

**对应课件**：L05

**算法要点**：N 个对等副本，每次写得到 W 个确认、每次读收集 R 个回复取最新版本。**W + R > N** 保证任意写法定人数和读法定人数至少有一个公共副本，所以读一定能看到最近成功的写。

**观察场景 A（避开最慢副本）**：node-1→node-5 链路延迟 3000ms，W=R=3（5 节点）；写操作只等最快的 3 个副本，约 200ms 返回，不用等 node-5 的慢速确认。再改为 W=5，感受等待最慢副本的代价。

**观察场景 B（W+R ≤ N 导致读到旧值）**：W=1，R=1；node-1 写 x=1 只确认自己；node-3 读 x 只问自己，此时 node-3 还没收到写，读到旧值。这不是 bug，是允许 W+R ≤ N 的必然代价——`lastGet.stale` 会标出这次读是过期的。

**观察场景 C（少数派分区不可用）**：W=R=3，分区 {node-1, node-2} | {node-3, node-4, node-5}；少数派这侧（node-1, node-2）凑不够 3 个写确认，操作失败。这是 CP（选择一致性牺牲可用性）的体现。

---

### 5.3 Basic Paxos

**对应课件**：L05

**算法要点**：两阶段单值共识。Proposer 先用 `Prepare{n}` 收集多数派承诺（n 必须比所有节点见过的提案号都大），再用 `Accept{n, v}` 让多数派接受值 v——v 取第一阶段里已接受的最高编号的值，若无则用自己想提的值。多数派接受后值被选定（chosen），Proposer 广播 `Decide` 通知。

**最重要的理解点**：任意两个多数派必相交（5 节点中任意两组 3 人都至少有 1 人重叠）。这个几何性质保证了第二个 Proposer 在 Prepare 阶段一定能从某个已接受过旧值的 Acceptor 那里得知旧值，从而沿用它——Paxos 的安全性完全建立在这一点上。

**观察场景 A–D（四种课件情形）**：

课件画了四种场景（Proposer 联系不同多数派时的情形）。建议按如下顺序操作：

- **情形 1**（尚无提案）：断开 N1 与 N4/N5 的链路，N1 `Propose(紫荆)`，完整跑完两阶段，N1-N3 三人共识。
- **情形 2**（已有选定值）：在情形 1 基础上，让 N4 以更高提案号 `Propose(澜园)`；N4 在 Prepare 时从 N3 得到 `<A 1.1 紫荆>`，于是沿用紫荆，所有节点最终共识紫荆。
- **情形 3**（看到尚未选定的值）：N1 在两阶段之间停顿（`pauseMs`），N4 趁机以更高提案号提议，由于 N3 已接受过 N1 的值，N4 必须沿用它。
- **情形 4**（没看到旧值）：调整链路让 N4 在 Prepare 时没有碰到任何接受过旧值的 Acceptor，于是 N4 提自己的值，最终选定 N4 的值，N1 的提案被拒绝。

每个情形操作后，在时空图里找到"选定点"：Accept 消息被第 3 个 Acceptor 接受的那一刻，就是共识达成的时刻。

**观察场景 E（活锁）**：关闭两个节点的退避，让它们同时用 `retry=true` 持续互相拒绝对方的提案号，循环升级。打开退避后，很快有一方率先完成两阶段。

**设计变体（持久化保障安全）**：这是最重要的变体。
1. 打开某节点的 `Amnesia`（不持久化承诺和投票）；
2. 让该节点参与了一次共识后崩溃重启；
3. 它忘记了自己的承诺，新 Proposer 在 Prepare 时拿不到旧值，选出了不同的值；
4. 于是两个不同的值都被"选定"——共识被破坏。

对照实验：用正常持久化，重启后承诺仍在，新 Proposer 正确沿用旧值，安全性保持。

### 5.4 Paxos 复制状态机 KV

**对应课件**：L05

**算法要点**：把 Basic Paxos 推广到多值。日志的每个槽位（slot）是一个独立的 Basic Paxos 实例。客户端发给任意服务器，服务器把操作提议到**自己还不知道已决定的最低空槽位**。如果被别人的操作抢先，就换下一个槽位重试。所有副本严格按槽位顺序执行日志，因此所有人以相同顺序执行相同操作。

**观察场景 A（依次写入与读取）**：
从不同节点依次发 Put / Get，观察日志 `log` 字段里槽位的分配。注意 Get 也占一个槽位——它需要和其他写操作排好顺序，才能保证读到正确版本（读日志是线性一致的关键）。

**观察场景 B（两个写入竞争同一槽位）**：
node-1 和 node-2 同时 `Put`，都提议槽位 1；只能有一个值被选定，输的一方在 Prepare 里看到对方已接受的值，帮它完成槽位 1，然后在槽位 2 提议自己的操作（`conflicts` 加一）。所有副本日志最终相同。

**观察场景 C（崩溃与追赶）**：
1. node-5 崩溃，其余 4 台继续提交槽位 2–4；
2. node-5 恢复后，下一次 Prepare 消息到达时，它发现自己有空洞，对每个空洞并发提议 no-op——Prepare 一定会从多数派里得到已选定的操作，于是 no-op 被替换为真实操作；
3. node-5 的日志追上，存储内容与其他节点一致。

**观察场景 D（少数派分区无法提交）**：
分区 {node-4, node-5} 与多数派隔离，发给 node-4 的写入拿不到多数派承诺，6 秒超时后报错。分区恢复后追赶同一日志。

### 5.5 两阶段提交（2PC）

**对应课件**：L05

**算法要点**：协调者（TM，node-1）先向所有参与者（RM）发 `Prepare`，收齐全部 `YES` 票才提交，任何一个 `NO` 都中止——**任何一方都能否决，多数不够**。关键决定在"提交点"：协调者把决定写入日志后才通知参与者；日志写下之前崩溃 → 中止（推定中止）；日志写下之后崩溃 → 恢复后重发 Commit 直到每个参与者确认。

这里实验的协议（node-1 = TM，其余 = RM，各持一个账户余额 100）可以模拟银行转账。

**观察场景 A（正常提交）**：
发起转账，在时空图里找到 Prepare / Vote(YES) / Commit / Ack 四种消息。时空图标签 `调用 RM.Prepare · {"txn":"T1","delta":-30}` 的回复 `{"vote":"yes"}` 就是投票。验证：两笔转账后余额守恒（总额 200 不变），三方对每笔事务的结局完全一致。

**观察场景 B（参与者否决）**：转出超过余额（余额不足投 NO），另一个参与者已投 YES 并加锁，但事务中止，锁被释放。问题：对比 Paxos/Raft 的多数派，为什么 2PC 必须等**所有人**投票，而不能像 Paxos 那样只等多数派？（提示：Paxos 选的是值，2PC 提交的是已经锁住资源的操作。）

**观察场景 C（协调者决定前崩溃，参与者阻塞）**：
1. 带 `pauseBeforeDecisionMs=30000` 发起转账，所有参与者投了 YES，协调者在写决定前停顿；
2. 此时崩溃协调者；
3. 参与者每 2 秒用 `TM.Status` 询问协调者，但得不到回复，进入 `uncertain` 状态，账户一直被锁——其他转账也无法进行；
4. 恢复协调者，它读日志发现 T1 没有决定，推定中止，参与者释放锁。

**观察场景 D（协调者提交点之后崩溃）**：
1. 带 `pauseAfterDecisionMs=30000` 发起转账，协调者已把 `commit` 写入日志，尚未通知就崩溃；
2. 参与者仍 `uncertain`，余额未变；
3. 恢复协调者，重发 Commit，参与者最终提交，余额变化。

对比场景 C 和 D：崩溃时间点不同，结果截然不同。事务在逻辑上的"提交时刻"是协调者写日志那一行，不是参与者看到 Commit 的那一刻。

**设计变体（参与者为什么在投 YES 之前写日志）**：
如果参与者投 YES 后、写稳定存储之前崩溃，它重启后没有 `prepared` 记录——它会认为从未参与过这个事务，推定中止并释放锁。但协调者可能已经收到所有 YES 票并决定提交，另一个参与者也已经提交了——数据不一致。

要演示这个问题需要修改协议代码，去掉 `sdk.Save` 的调用，然后在投票后立刻崩溃该节点，再恢复。思考：这和 Paxos 的 Amnesia 场景有什么相似之处？

## 七、常见问题

**Q：运行时看不到任何消息，节点一直是初始状态？**

确认 Docker Desktop 已启动。L05 复制与共识协议是自定义 Go 项目，必须使用「本机 Docker」或 Kubernetes 运行环境，**不支持「内置仿真」**（仿真模式仅适用于平台自带示例 raft-election、netrpc-token、lww-store、grpc-broadcast）。L03/L04 的协议也是自定义 Go 项目，同样需要 Docker。

**Q：时空图上的箭头很密，看不清？**

用「筛选节点」只显示几个节点，或者缩放时间轴（默认每屏 1 秒，可以改为 2/5/10 秒）。勾选「隐藏心跳与回复」可以过滤掉周期性的心跳消息。

**Q：场景里的"崩溃后恢复"，节点状态面板还显示旧数据？**

崩溃后节点面板显示的是它最后上报的状态，直到恢复后进程重新 `Report`。如果你的协议在重启时没有立刻上报，面板会延迟更新。可以在协议代码里在启动时主动调用一次 `node.Report(...)`。

**Q：想演示消息乱序，但平台默认是 FIFO 的？**

默认每条有向链路保持 FIFO（每个链路上的消息按发送顺序到达，不会乱序）。要开启乱序，在 `scenarios.json` 的 `settings` 里加 `"network": {"ordering": "unordered", "reorderRate": 0.5, "reorderMin": 100, "reorderMax": 500}`，或通过平台 API 的 `fault(kind: 'network', network: {...})` 动态设置。详见 `docs/PLATFORM-API.md`。

**Q：`sdk.Save` / `sdk.Load` 的数据保存在哪里？重启后会丢失吗？**

保存在容器的 `/state/` 目录（Docker 模式），容器崩溃后重启时 `/state/` 里的内容保留，Go 程序可以用 `sdk.Load` 读回。结束实验会清理容器，数据丢失。

**Q：协议代码改了，旧的运行记录会变吗？**

不会。每次运行时平台会把当时的代码快照保存在 `data/<run-id>/source.json`，历史回放永远使用运行时的代码快照，不受之后的修改影响。

### 场景文件速查

```json
{
  "scenarios": [{
    "id": "my-scenario",
    "name": "我的场景",
    "settings": {"nodeCount": 3, "latency": 200},
    "steps": [
      {"note": "说明文字，不执行任何操作"},
      {"input": {"node": "node-1", "method": "Application.Put", "values": {"key": "x", "value": "1"}}},
      {"concurrent": [
        {"node": "node-1", "method": "Application.Acquire", "values": {"holdMs": 2000}},
        {"node": "node-3", "method": "Application.Acquire", "values": {"holdMs": 2000}}
      ]},
      {"fault": {"kind": "crash", "node": "node-2"}},
      {"fault": {"kind": "link", "from": "node-1", "to": "node-3", "blocked": true, "bidirectional": true}},
      {"wait": 3000},
      {"until": {"node": "node-1", "path": "role", "value": "leader"}, "timeout": 15000},
      {"check": {"atMostOne": {"path": "role", "value": "critical"}}, "label": "互斥始终成立"}
    ]
  }]
}
```

字段说明（以 `scripts/scenarios.mjs` 实现为准）：

- `input` / `concurrent`：按 `method`（RPC 标签，如 `Application.Acquire`）找到节点声明的动作；`concurrent` 中的输入在同一协调器时刻送达。`"await": false` 不等待返回；`expect` 可为 `ok`、`error`、`timeout`；`timeout` 默认 20000ms。
- `fault`：与平台故障 API 相同，`kind` 为 `crash`、`recover`、`link`、`heal`、`network`、`channel`。link 省略的字段取实验默认值，`blocked` / `bidirectional` 默认 false。
- `note` 只打印说明；`wait` 等待固定毫秒数；`until` 轮询直到条件成立或超时（默认 20000ms）；`check` 立即断言。`label` 为输出中的说明文字。
- 条件：
  - `{node, path, op, value}`：`node` 可为节点名、`"*"`（全部在线节点都满足）、`"any"`（任一在线节点满足）或数组；`op` 默认 `==`，支持 `== != < <= > >= abs<= abs> includes exists missing in`；`path` 为点分路径（如 `lastSync.rttMs`）。
  - `{same: path}` / `{differ: path}`：节点（默认全部在线节点，可用 `nodes` 指定）该字段全部相同 / 不全相同。
  - `{messages: {method, op, value}}`：RPC 请求计数，`op` 默认 `>=`。
  - 历史不变式 `{atMostOne: {path, op, value}}` / `{moreThanOne: {...}}`：在整个运行历史中，同时满足条件的节点始终至多一个 / 曾经多于一个。
  - 组合：`{all: [...]}`、`{any: [...]}`、`{not: {...}}`。
