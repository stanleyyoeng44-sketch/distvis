LAB 1 · EXPERIMENT RECORD · 29 OCTOBER 2026

Lamport mutual exclusion

Verified behavior of a timestamp-ordered distributed lock [a protocol that permits only one node to execute a protected operation at a time], plus its release-free Ricart–Agrawala comparison.

All seven scenarios passed

Every scenario ran twice against real Go programs in Docker. The final evidence set contains seven completed runs, with no overlapping critical sections [intervals when nodes hold the protected operation]. State-report ordering and each node’s message counter were independently checked against the exported event histories.

These are observations from specific executions, not a proof of correctness for every possible execution or a production-readiness claim.

Configuration and provenance

All experiments used 3 nodes, 80 ms fixed latency, 128 KiB/s per directed link, and seed 42. A fixed seed does not make Go scheduling deterministic. The exported runs used protocol revision 2; every exported Go file matched the reviewed local implementation byte-for-byte. Revision 3 adds a rule excluding the old compiled executable from version control; its Go implementation is unchanged.

Counts include outgoing Request, Ack, and Release calls across all nodes, including failed attempts. Automatic RPC responses [the library’s return messages] and cancellation envelopes are excluded.

A. Concurrent requests

In a fresh default-mode run, node-1 and node-3 received concurrent Acquire(holdMs=2000) inputs. Both requests had timestamp 1, so node-1’s smaller numeric ID gave it priority. Its wait was 170.976 ms; node-3’s was 2259.764 ms. Both completed once, all queues emptied, and the entire recorded state history showed at most one critical node.

The application calls returned acceptance in about 4.21 ms each. Acceptance means the background operation started, not that the lock was already acquired. Node-1’s entry and exit were events 67 and 76; node-3’s were events 94 and 104.

B. Uninvolved node crash

Node-3 was crashed while idle, then node-2 requested entry. Node-2 received one of two required permissions, reported missingAcks=["node-3"], and remained at entries=0. After roughly three seconds, its state identified the failed request to node-3; observation continued beyond ten seconds without entry. The accepted application input did not time out while the protocol continued waiting.

This also corrects the old combined report’s node names: its saved crash export used node-3 crashed and node-2 requesting. A finite experiment cannot observe “forever”; the missing-permission wait and absence of retransmission explain why this request cannot finish while that permission remains missing.

C. Blocked link and healing

Both directions between node-2 and node-3 were blocked before node-2 requested entry. Node-2 could not obtain node-3’s permission and never entered. The links were healed at event 37, but four additional seconds of observation still showed a waiting operation because the discarded request was not retransmitted. Restoring connectivity does not replay a message lost earlier.

This is a direct-link failure, not a complete split into disconnected groups: node-1 retained its links. The protocol does not route the missing request through node-1.

D. Message-overhead comparison

One default-mode acquisition sent 2 Request, 2 Ack, and 2 Release messages: 3(n−1) = 6. In a fresh run, all three nodes selected ricart-agrawala before any requests. The equivalent acquisition sent 2 Request and 2 Ack calls, with no Release: 2(n−1) = 4.

The variant also removes the remote-request queue and queue-head entry check. Deferred acknowledgements [permissions withheld until the holder leaves] enable the next request. Deleting only Release from the original queue-based implementation would leave stale requests blocking progress. A second variant experiment completed nine competing acquisitions with 36 messages and no overlap.

Classic Lamport normally uses immediate replies with reliable FIFO links [messages on a directed connection arrive in send order]. This lab-oriented implementation follows the handout’s deferred-permission emphasis while retaining the Lamport queue and explicit releases; that distinction is documented.

Regression checks

A 15000 ms hold returned acceptance in 7.49 ms, remained critical after eleven seconds, and subsequently completed without an application deadline error. Its recorded critical interval was about 14.991 seconds; these coordinator-observed report times include scheduling and transport effects rather than directly measuring the Go timer.

Each node’s report sequence increased throughout every run, and its final message counter equaled its recorded sends. Non-fault runs had zero outgoing-call errors. Local checks passed the full Go test suite with the race detector [a checker for unsynchronized shared-memory access] three times, static checks, and twenty repetitions of the concurrency/report tests.

Limits that remain intentional

  • Every peer’s permission is required. Ignoring a failed node would change the exclusion argument.
  • Timeout means the remote outcome is unknown. The remote method may have run even if its response was lost.
  • No persistent recovery state, automatic retries, changing membership, or crash/restart safety is implemented. A restarted process forgets its queue, clock, and chosen mode.
  • Healing a link does not restore progress after a discarded protocol message. Use a fresh run after the failure demonstrations.
  • “Completed” describes the local cycle; it does not prove every remote release arrived. Check errors and remote queues as well.
